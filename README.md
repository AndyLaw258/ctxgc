# ctxgc

**Context Garbage Collector** —— 审计 AI Agent 的上下文成本。

> 现有所有 token 统计工具都算**体积**。但决定开销的是**这东西在上下文里待了多久**。
> ctxgc 把成本从 `体积 × 单价` 扩展为 **`体积 × 存续轮数 × 单价`**，给出逐条归因，
> 并用真实调用序列**重放**另一种上下文策略，回答"治理之后能省多少"。

---

## ⚠️ 先说清楚：它自己不省任何 token

**这是仪表盘，不是发动机。** 装上它不会让你的账单变小一分钱 —— 它只负责让"钱花在哪"从猜测变成可测量的事。

四条路径里，**只有第三条真的省**，而省下来的活是**你（或 agent）干的**，不是它干的：

| 路径 | 做什么 | 省 token 吗 |
|---|---|---|
| ① 看得见 | 审计上下文成本 | ❌ 只是测量 |
| ② 证得了 | 反事实模拟"治理后能省多少" | ❌ 是**假想**，不是节省 |
| ③ **改方法** | 工作流体检 → 促使行为改变 | ✅ **间接省** —— 它指出该改哪里，改的是你 |
| ④ 改机制 | 句柄化治理（工具结果落盘） | ⬜ 未实现（DSH 无 hook） |

**一笔实测账**（一天的真实会话，每轮新增上下文从 2.14k 降到 1.43k）：

| 省下的部分 | 实际是谁做的 | ctxgc 的角色 |
|---|---|---|
| 助手输出 −26% | agent 改变了回复习惯 | 量出来给它看 |
| 工具结果 −51% | 改变了命令写法（先聚合再读） | 量出来给它看 |
| `AGENTS.md` 每轮 −219 token | 手工去重与压缩 | 量出价码 |
| 工具结果被自动裁剪 | **DSH 内置的 `tool-result-pruner`** | **发现了它的存在** |

**每一笔节省，动手的都不是 ctxgc。**

### 那"能自动省 token"的那一层在哪

**在 Agent 运行时里，不在本工具里。** DSH 自带 `dsh-compaction-tool-result-pruner`（`standard` preset 默认挂载：工具结果超 8192 字符就只留头 4096 + 尾 1024，压缩触发时执行）。

ctxgc 对它的贡献是**发现它已经装好了、发现它的触发点很晚、并把这个事实写进文档** —— 于是你不会再去重复造一个。这也是本工具不做治理机制的原因：那个位置已经被占了。

### 报告里的"可避免量"是**上界**，不是已省下的

它回答的是"**如果**每条工具结果都摘要化，能少读多少" —— 一个假设。真实收益必须靠治理机制落地后的**开/关对照实验**确认。README 里所有这类数字都标了"上界"。

## 一、问题：被少算的那一半

一条 12,512 token 的目录列表，如果只出现一次，成本就是 12,512。

但它出现在第 2 步，而这次会话一共有 108 步 —— 它会被**重读 106 次**。

体积视角看不到这个差别。以下是 ctxgc 在一个真实会话（108 次模型调用）上的实测输出：

| 类别 | 体积 | 累计读取 | 放大 |
|---|---|---|---|
| **助手输出** | 140.0k | **6.73M** | 48.1x |
| 工具结果 | 65.1k | 4.91M | 75.4x |
| 系统提示词 | 7.18k | 775.4k | 108.0x |
| 用户消息 | 775 | 54.3k | 70.1x |
| **合计** | 214.2k | **12.59M** | **58.8x** |

**结论会翻转**：按体积排，工具结果是最大来源；按生命周期排，**助手输出反超**。
只算体积的工具，会把优化火力对准错误的目标。

## 二、原理

### 成本模型

```
成本 = 体积 × 存续轮数 × 单价
       ↑        ↑
    所有人都在算  没人算
```

`存续轮数` = 该内容从进入上下文起，到会话结束被重读的次数。

### 精确归因（不是估算）

DSH 每次模型调用都会上报用量，且满足恒等式：

```
totalTokens = inputTokens + cacheReadTokens + outputTokens
```

因此**模型这一次实际看到的上下文大小**可以精确算出：

```
contextSize(n) = totalTokens(n) - outputTokens(n)
```

相邻两次调用的差值，就是「上一步产出的全部内容」的真实 token 成本：

```
growth(n) = contextSize(n) - contextSize(n-1)
```

左边界是闭区间 —— 上一步**模型自己的输出**（助手回复 + 工具调用参数）同样会被后续每一次调用读到，必须计入。漏掉它会让账面体积只有实际的一半。

### 自检不变式

各条目「进入时的体积」之和，应当等于上下文最终大小：

```
Σ growth = finalContextSize
```

实测偏差 **+0.0%**。报告里会打印这行对账，偏差过大说明存在上下文收缩或漏归因。

## 三、安装与使用

零第三方依赖，Node ≥ 22.19。

```bash
git clone <repo> && cd ctxgc
node bin/ctxgc.js              # 审计最近一个会话
node bin/ctxgc.js simulate     # 反事实模拟：治理后能省多少
node bin/ctxgc.js workflow     # 工作流体检：记忆外置做得怎么样
node bin/ctxgc.js prompt       # 常驻成本审计：每轮固定烧掉多少
node bin/ctxgc.js init         # 生成记忆外置工作区骨架（不覆盖已有文件）
node bin/ctxgc.js all          # 全部会话总览
node bin/ctxgc.js list         # 会话清单
node bin/ctxgc.js --top 30     # 加长排行榜
node bin/ctxgc.js --json       # 机器可读输出
```

`npm link` 之后可直接使用 `ctxgc` 命令。

### 常驻成本审计（v0.6）

系统提示词里有一部分**每一轮都要付一次钱**。难点不在算，而在**取对数据源** ——
会话日志只落了其中一块：

| 部分 | 来源 | 只读日志会怎样 |
|---|---|---|
| 工具定义 | `request/header` 事件的 `data.header.tools` | **完全看不到** |
| 系统提示 | `system/message` 事件（注意是 `data.message.content`） | ✅ 只有这块能看到 |
| 工作区约定 | 文件系统的 `AGENTS.md` | **完全看不到** |

实测三者比例约为 **7.5 : 2 : 0.7**。只读日志会把每轮固定开销**低估到实际的三分之一** ——
而取错来源不会报错，只会安静地少算，所以每条来源都有单独的测试钉住。

```
  每轮固定开销
    部分            项数      字符   ≈token/轮    本会话累计
    工具定义          27    28,462       7,118         1.60M
    系统提示           2    14,463       1,860        418.5k
    工作区约定         2     1,306         702        157.9k
    ────────────────────────────────────────────────────────────────
    合计                                 9,680         2.18M
```

**能优化的只有你自己那一部分**：工具定义属于 profile 的插件开关（用不到的工具插件可以关掉，每关一个是每轮省一次），`AGENTS.md` 是纯文本（读一次就够的说明该下沉到 `memory/` 按需读取）。由 DSH 决定的部分不提建议 —— 提了也做不到。

> token 是**估算**（CJK 约 0.7/字，其余约 4 字符/token），不是 DSH 上报的真实用量 ——
> 工具定义与系统提示都不单独上报。比例可信，绝对值仅供参考。

### 适配任意运行时（v1.0）

核心与「读懂某种日志」是分开的，两者之间只有一层**中间表示（IR）**：

```
核心（成本模型 · 归因 · 生命周期 · 模拟 · 报告）
        ▲
        │  IR   ← lib/ir.js
   ┌────┴─────┐
dsh 适配器   通用适配器
```

换一个 Agent 运行时**不需要改核心** —— 把它的日志转成标准 JSON 即可：

```bash
ctxgc --runtime generic --sessions <目录>
```

目录里一个文件一个会话：

```json
{
  "id": "session-2026-09-22",
  "cwd": "C:/work/project",
  "calls": [
    { "contextSize": 12345, "outputTokens": 200, "readTokens": 12145, "cacheReadTokens": 10000 }
  ],
  "items": [
    { "enteredAtIndex": 3, "kind": "tool:read", "label": "读取配置", "tokens": 500, "bytes": 1800 }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `calls` | 模型调用序列。**唯一能算出真实上下文大小**的来源（`contextSize = total − output`） |
| `items[].enteredAtIndex` | 第几次调用时进入上下文（从 0 数）。**存续轮数完全依赖它**，填错的代价是报告数字全错 |
| `items[].kind` | `tool:<工具名>` 表示工具结果，其余固定值见 `lib/ir.js` |
| `items[].tokens` | 该条目的体积。**估算值**即可 —— 成本模型关心的是它 × 存续轮数 |

缺 `calls` 或 `items` 会**直接报错并指出缺哪个**：文件是你自己生成的，静默容错只会让你对着空报告猜。

**为什么不做「再写一个 Claude Code 适配器」**：适配器对不对，只能靠**真实日志样本**检验。手上没有样本时写出的适配器是不可验证的代码 —— 与这个项目「先测量、再断言」的原则相悖。通用适配器把这一步交还给使用者：写 20 行转换脚本，格式对不对一眼能看见，而且立刻能跑出结果。

### 版本韧性（v1.1）

DSH 的日志格式已演进到 v3 —— 它自带 `dsh-session-format*`：每版 codec **frozen**、逐级迁移链（v0→v1→v2→v3）、外加一个 catalog。也就是说格式演进是**被管理的**，不是随机故障；但 ctxgc 依赖它，仍然要有防御。

| 层 | 做什么 | 状态 |
|---|---|---|
| **① 结构容错** | 扫 `session.v*.jsonl[.zstd\|.gz]` 取**版本号最高**的（按数值比，`v10 > v9`）；解压按**魔数**分派（zstd / gzip / 未压缩） | ✅ |
| **② 失效发声** | 对账偏差超 ±2% 就报警，并指出最可能的原因（未知事件类型，还是归因逻辑本身） | ✅ |
| **③ 对接官方 codec** | 直接用 `dsh-session-format-catalog` 解码，格式升级由 DSH 负责 | ⬜ **暂缓** |

**为什么 ② 比 ③ 重要**：格式升级最危险的后果**不是崩溃，而是静默少算** —— 认不出的事件被丢掉，报告给出一个偏低的、却看起来完全正常的数字。一个会崩的工具你立刻知道它坏了；一个数字偏低的工具你会照着它做决策。

**一条踩过的坑**：② 的第一版把「未知事件类型」当作独立警报，结果在一个**数字完全正确**的真机会话上误报 —— DSH 有一大批**不进上下文**的元事件（`tool/call`、`request/header`、`agent/inbox/spliced`…），它们本来就不该被归因。**一个总在喊狼来了的自检层比没有更糟**：使用者会学会忽略它。现在未知类型只在**对账确实对不上**时才作为线索列出。

**③ 为什么暂缓**：它要引入对 DSH 包的依赖，丢掉「零第三方依赖」这个卖点；而 codec 的输出未必是 IR 的形状，还要再转一层。① ② 已覆盖「改文件名 / 换压缩 / 新增事件类型」三种情况，**只剩「字段语义变了」需要人工介入** —— 而那时对账会报警并指向适配器。代价与收益不成比例。

> token 数是估算、日志格式可能变、只能事后审计 —— 这三条已知局限没有消失，但前两条现在**有机制兜着**：数字偏了会报，格式变了能读。

## 四、反事实模拟：治理之后能省多少

审计回答「浪费了多少」，模拟回答「**治理之后能省多少**」。

它不是估算 —— 而是用这条会话**真实的调用序列**与**真实的归因数据**，重放另一种上下文策略：

```
策略：每条工具结果在上下文里最多保留 digest 个 token，其余落盘待取
重放：条目模拟体积 = min(实际体积, digest)
      第 k 步上下文 = Σ { 模拟体积 | 该条目在 k 步或之前已进入 }
```

### 实测：敏感性分析

| 摘要体积 | 模拟总读取 | 节省 | 降幅 |
|---|---|---|---|
| 全落盘 | 11.56M | 6.51M | **36.0%** |
| 100 | 12.21M | 5.86M | 32.4% |
| **300** | 12.92M | 5.15M | **28.5%** |
| 1000 | 14.33M | 3.74M | 20.7% |
| 4000 | 16.12M | 1.95M | 10.8% |

### 实测：按工具汇总（哪类工具最费）

| 工具 | 条数 | 体积 | 累计读取 | 放大 |
|---|---|---|---|---|
| **pwsh** | 55 | 29.9k | **3.46M** | **116.0x** |
| web_fetch | 7 | 19.1k | 1.65M | 86.0x |
| read | 12 | 12.8k | 1.05M | 82.5x |
| grep | 8 | 2.98k | 240.7k | 80.8x |
| write | 27 | 723 | 36.2k | 50.1x |

**结论直接可用**：`pwsh` 的目录列举类调用是头号目标 —— 55 条结果，平均被重读 116 遍。

### 为什么这个模拟可信

三条交叉验证，任何一条不成立结果就作废：

| 验证 | 实测 |
|---|---|
| `Σ items.tokens × reads == 累计读入`（两个独立算法算同一量） | 18.07M == 18.07M ✓ |
| `Σ growth == finalContextSize`（归因完整性） | 偏差 +0.0% ✓ |
| 基线重放 == 日志上报（重放不改动基础数据） | ✓ 一致 |

### 它**不能**证明什么

模拟假设「落盘的内容随时可取回」，因此不损失信息。但真实收益必须由治理机制落地后的**开/关对照实验**确认 —— 尤其要验证：

- 取回机制是否引入额外调用（省了读取，多了往返）
- 任务成功率是否下降
- 模型在缺少细节时是否更容易走弯路（圈数变多，反而更贵）

**这一层是模拟给不了的，必须真跑。** 见路线图 v0.4。

## 五、工作流审计：验证「记忆外置」到底省了多少

### 为什么需要这一层

审计能算出上下文里的浪费，模拟能算出治理后的收益 —— 但两者都管不到**你怎么工作**。

而实践中最大的一笔节省，来自工作方式本身：

| 做法 | 后果 |
|---|---|
| 信息堆在对话历史里 | 每轮重读，成本 × 存续轮数 |
| **信息放文件系统，按需读取** | 对话保持短，成本与轮数脱钩 |

这套方法有效，但有个致命短板：**没有度量**。做了却不知道省了多少、哪部分最有效。

### 结构四要素

```
工作区/
  AGENTS.md     自动入口   ← DSH 每个新会话自动注入，不靠人提醒
  memory/       长期记忆   ← 项目背景、约定、踩过的坑（替代"翻聊天记录"）
  skills/       可复用流程 ← 做对过的步骤固化下来，不重新摸索
  sessions/     产出归档   ← 一次工作一个文件夹，下次能找到
```

`ctxgc init` 生成骨架，**已存在的文件一律不覆盖**。

### 四个可计算指标

| 指标 | 算法 | 高值说明 |
|---|---|---|
| **背景重述成本** | **每条用户消息的平均 token** | 每次都在重新交代背景 → 记忆没外置 |
| **重复获取** | 同一目标被读取多次 | 结果没沉淀 → 该固化到 memory/skills |
| **上下文启动成本** | 首次调用的上下文大小 | 入口过重，细节应下沉到 memory/ |
| **结构健康度** | 四要素是否健全（必需项权重加倍） | 产出散落，下次找不到 |

> **为什么用平均值而不是占比**：占比（用户消息 ÷ 上下文总量）的分母会被每轮累积的助手输出撑大，
> 会话越长数字越小。实测**同一个会话**里从 9.0% 掉到 2.0%，而用户消息的绝对长度毫无变化 ——
> 它测的是"上下文被谁占据"，不是"用户是否在重述背景"。
> 占比因此降级为报告里的**参考项**，并在输出中直接注明"不可用于判断趋势"；判定改用不受会话长度影响的平均值。

### 重复检测的精度（踩坑记录）

这个功能连续误报过两次，两次都被测试锁死：

| 版本 | 误报 | 原因 |
|---|---|---|
| v1 | **46 次** | 用截断到 96 字符的 `label` 做指纹，不同长命令前缀相同 |
| v2 | **3 次** | 只取第一个参数，同目录不同 pattern 的 `grep` 被判为重复 |
| v3 | **2 次** ✅ | 按工具选「真正决定返回什么」的参数（`grep` 用 `pattern+path`） |

现在只有白名单内的读取类工具参与检测，且 `edit`/`write` **天然无指纹** —— 同一文件被反复编辑不会被误判（实测：一次重构里同一文件编辑 9 次是健康的）。

## 六、设计

四条路径，从"看见"到"改变"：

```
① 看得见  ── 审计引擎                                     ✅ v0.1
     多帧 zstd 解码 → 用量归因 → 生命周期成本 → 排行榜

② 证得了  ── 反事实模拟                                   ✅ v0.2
     用真实调用序列重放另一种策略 → 敏感性 → 增长曲线 → 治理排行

③ 改方法  ── 工作流审计 (结构性治理)                        ✅ v0.3
     记忆外置 + 流程固化 + 产出归档 → 四个可计算指标 → 体检与建议
     ⭐ 不需要任何 hook，改的是工作方式，不是运行时

④ 改机制  ── 句柄化治理 (技术性治理)                        📋 v0.5
     工具结果结构化落盘 + 上下文只留句柄（指针 + 摘要 + 体积）
     ⚠️ 前置未决：DSH 无工具结果中间件钩子，需另找插手路径

⑤ 真跑    ── 开/关对照实验                                 📋 v0.4
     同一任务跑两组：token 降多少？成功率掉没掉？圈数有没有变多？
```

**③ 和 ④ 是互补的两条治理路径**：③ 改信息组织方式（治本，靠约定），④ 改运行时机制（治标，靠代码）。
③ 现在就能用，④ 卡在技术上；而 ② 正好是验证 ③ 效果的工具。

### 顺带解决的一个坑：多帧 zstd

DSH 的会话日志是「无结束标记的多帧 zstd 增量流」——每追加一批事件就往文件尾拼一个独立帧。因此文件里没有总帧头，Node 自带的 `zstdDecompressSync` / `createZstdDecompress` 都只解出**第一帧**就停。

> 实测：一个 897 KB 的日志只能解出 **209 字节**，恰好是会话头。

做法是扫描帧魔数（`28 B5 2F FD`）逐帧独立解压后拼接，对每个候选位置 try/catch（压缩数据内部理论上可能出现相同字节序列）。

## 七、已知局限（诚实清单）

| 局限 | 说明 |
|---|---|
| **依赖 DSH 日志格式** | 事件 schema 与 `usage` 字段属于内部格式，版本升级可能变动。模块已按字段缺失做了降级，但仍需跟进 |
| **分摊是估算** | `growth` 按窗口内字节占比分摊到条目上。同一步内多条目时，分配比例是近似的 |
| **收缩场景会低估** | DSH 触发上下文压缩时，`growth` 为负，该步按 0 计（报告会提示收缩次数） |
| **只能事后审计** | 读的是已落盘的会话日志，无法实时干预正在进行的会话 |
| **"可避免量"是上界** | 它回答的是"若每条工具结果改为摘要形态能少读多少"，不等于实际能省下的钱 |
| **未做跨会话去重** | 同一份信息在多个会话里重复获取的情况没有合并统计 |
| **模拟假设可无损取回** | 反事实模拟建立在「落盘内容随时可取回」之上；若真实取回机制引入额外往返调用，收益会缩水。这正是 v0.4 必须真跑的原因 |

## 八、它不是什么

- **不是**提示词压缩工具。不修改、不摘要、不改写你的任何内容。
- **不是**成本预测器。它算的是已经发生的读取量，不做未来预估。
- **不是**治理工具 —— **它自己不省一个 token**（详见开头的「先说清楚」）。它让浪费可见、可归因、可验证；动手的是你或你用的 Agent 运行时。
- **不是**仅针对 DeepSeek 或 DSH。归因方法依赖「每次调用上报用量」这一普遍能力，DSH 只是第一个适配的数据源。
